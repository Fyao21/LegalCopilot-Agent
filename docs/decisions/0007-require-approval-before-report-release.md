# ADR 0007：报告必须批准后才能发布

- 状态：已接受
- 日期：2026-07-31
- 适用版本：1.0.0 起

## 背景

0.9.0 及以前的流程在报告生成后直接把内容视为最终结果。即使法规引用已经过数据库原文校验，模型仍可能在事实归纳、风险判断或建议措辞上出错。法律分析属于高风险内容，不能把“引用真实”误当成“整份报告已经可以发布”。

项目还需要处理三个工程问题：

1. 审核人可能要求修改，而旧报告不能被静默覆盖；
2. 浏览器超时重试或两个页面同时审批时，不能执行两次；
3. 服务重启后，等待审批的任务必须能从原 checkpoint 继续。

## 决策

在 `write_report` 后增加 `approve_report` LangGraph interrupt。报告生成后进入 `waiting_for_approval`，人工只能选择：

- `approve`：批准当前版本，任务完成；
- `request_changes`：保留当前版本，生成下一版本后再次等待审批；
- `reject`：终止任务并保留审计记录。

业务数据使用 `report_versions` 保存不可变报告快照，使用 `agent_approvals` 保存每轮决定、意见、审核人和幂等键。`AgentRun.current_report_version` 指向当前草稿，`approved_report_version` 只在批准后设置。

导出接口只读取 `approved` 版本。未批准草稿和被驳回报告可以在页面查看和审计，但 Markdown/PDF 导出返回 409。

审批写入同时采用两种并发保护：

- `Idempotency-Key`：识别同一客户端请求的网络重试；
- `state_version` 条件更新：保证不同页面竞争同一待办时只有一个成功。

## 为什么不直接覆盖一列 report_markdown

单列覆盖无法回答“谁在什么时候改了什么”，也无法稳定生成版本差异。追加版本记录让 V1、V2 和最终批准版本都可追溯，适合审计和面试演示；代价是需要更多表、查询和状态一致性处理。

## 后果

正面影响：

1. 模型输出与正式发布之间有明确边界；
2. 退回修改保留完整版本链和统一 diff；
3. 审批待办可以跨服务重启恢复；
4. API 重试和并发审批不会重复推进工作流；
5. 前端能明确区分草稿、已批准和已驳回状态。

代价与限制：

1. 本地版只有审核人名称，没有登录鉴权和 RBAC，不能用于真实生产审批；
2. SQLite 适合单机演示，高并发场景应迁移 PostgreSQL；
3. 当前修改意见以整份报告重写为单位，尚未实现段落级批注和部分批准；
4. 后台任务仍在 FastAPI 进程内，生产环境需要持久任务队列。

## 验证

`tests/test_sixth_week.py` 覆盖批准、退回生成 V2、驳回、未批准禁止导出、幂等重放、乐观锁冲突和跨应用重启恢复。统一自测入口共 69 项测试。
