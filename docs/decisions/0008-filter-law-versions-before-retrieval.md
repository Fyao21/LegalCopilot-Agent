# ADR 0008：法规版本必须在召回前按案件日期过滤

- 状态：已接受
- 日期：2026-07-31
- 适用版本：1.1.0+

## 背景

法律 RAG 的相似度不能代替法规效力判断。同一问题可能同时匹配已废止的旧法和现行新法；如果先对全部条文计算 Top-K，再删除日期不适用的结果，旧版本可能已经挤掉真正适用的条文，过滤后只剩不足 K 条。

只在 Citation 中保存 `article_id` 也不够。报告需要回答“案件按哪个日期分析、引用的是法规哪一版、该版本当时为什么有效”。

## 决策

1. 使用 `laws` 表示稳定的法规实体，使用 `law_versions` 表示具体版本。
2. `legal_articles.law_version_id` 将条文绑定到精确版本。
3. 版本有效区间统一使用半开区间 `[effective_from, effective_to)`：
   - `effective_from <= as_of_date`；
   - `effective_to IS NULL OR as_of_date < effective_to`。
4. `as_of_date` 可选；用户未填写时检索服务使用服务器当前日期，已有调用不需要修改。
5. SQL 在关键词和向量打分前过滤不适用版本。
6. Citation、检索日志、Agent 引用和报告引用快照保存 `law_version_id`。
7. 历史版本可以在历史有效期内返回；它的当前状态仍显示 `repealed`，界面补充“在所选历史时点有效”，避免误认为现行法。

## 后果

正面影响：

- 日期边界可通过确定性测试验证；
- 已废止条文不会作为当前有效结果返回；
- 同一问题按不同日期可以得到可解释的版本差异；
- 报告保留可追溯的版本证据链；
- 时间过滤不会浪费 Top-K 候选。

代价与限制：

- 导入法规时必须维护版本元数据；
- 当前教学版使用一部旧法到一部新法的替代关系，没有完整处理同法修订、多司法辖区和溯及力例外；
- `status` 表示版本当前生命周期，历史查询仍需结合日期区间理解；
- 版本数据本身可能过期，仍需要权威来源同步与人工复核；
- SQLite 运行时迁移只能做增量字段和索引，生产环境应使用 Alembic。

## 被拒绝的方案

### 先 Top-K，再过滤

实现简单，但会导致有效候选在召回阶段被失效版本挤掉，因此拒绝。

### 只在 `legal_articles` 增加生效和失效日期

无法复用法规实体信息，也难以表达替代关系和同一法规的多版本，因此拒绝。

### 把版本判断交给 LLM

模型可能使用过时知识，也无法形成可审计的数据库条件。版本过滤属于确定性业务规则，不应由生成模型决定。

## 迁移条件

进入生产法规库前需要补充：

- 官方来源标识、公布日、核验时间与内容哈希；
- `(law_version_id, article_number_normalized)` 唯一约束；
- 同法修订、废止决定、司法解释和地区适用关系；
- 来源过期提醒与受审计的版本同步任务；
- PostgreSQL/Alembic 迁移和时间查询索引。
