## 2. 先准备好项目介绍

### 2.1 30 秒版本

> 我做的是一个可追溯的法律分析 Agent，解决大模型直接回答时法条可能编造、引用版本与案件时间不匹配、信息不足仍强行作答，以及模型草稿未经复核就发布的问题。系统用 LangGraph 把案件抽取、用户追问、按日期筛选法规版本、混合检索、引用审核、报告生成和人工审批拆成有状态节点。每条引用必须关联 article ID 与 law version ID，回答和审批都能从 SQLite checkpoint 恢复。OpenTelemetry Trace 还能定位节点耗时、模型、Token、人民币费用和降级。项目有 React 前端、FastAPI 接口、24 条脱敏评测集和 84 项自动测试。

### 2.2 90 秒版本

> 项目输入是案件问题以及可选的 TXT、DOCX 或带文本层 PDF，输出是包含案件摘要、争议焦点、法律分析、证据缺口和可核验法条的 Markdown/PDF 报告。
> 第一层是案件抽取，Agent 模式调用结构化 LLM，离线模式使用规则；模型字段为空或 Schema 错误时会修复或透明降级。第二层是时态 RAG，先按案件日期筛选有效法规版本，再使用关键词分数和 Embedding 余弦相似度做混合检索。第三层不是直接相信模型，而是用 article ID 和 law version ID 回查数据库，核对版本、名称、条号和正文，报告只使用审核通过的引用。
> 第五周我增加了 Human-in-the-loop：缺少交货期限等关键事实时，LangGraph interrupt 保存 checkpoint，任务进入 waiting_for_user。回答接口使用幂等键处理网络重试，用 state_version 乐观锁处理两个页面并发提交，再通过 Command(resume) 恢复同一个 thread。服务重启后仍能继续原任务。
> 第六周我增加了第二个人工节点：报告写完后进入 waiting_for_approval，审核人可以批准、退回修改或驳回。退回不会覆盖旧报告，而是生成新版本并再次等待审批；只有 approved 版本可以导出。审批接口同时使用幂等键和 state_version，避免网络重试或多个页面并发审批造成重复版本和状态覆盖。
> 第七周我把法规实体与版本拆表，使用 `[effective_from, effective_to)` 表达效力区间，并把日期过滤放在召回前。相同解除合同问题在 2020-12-31 返回历史合同法，在 2021-01-01 返回现行民法典；引用、报告快照和前端都保存精确版本证据。
> 当前版本适合本地工程演示，提供 36 条内置教学法规、200 条跨领域生成样例、24 条评测案例和 84 项测试；生产化仍需要 PostgreSQL/pgvector、持久任务队列、登录鉴权与 RBAC、法规官方同步，以及 OTLP/告警平台。

### 2.3 介绍时不要犯的错误

- 不要先念 FastAPI、LangGraph、React 等技术栈；先讲问题、输入、输出和可信性约束。
- 不要说“完全杜绝法律幻觉”；应说“减少引用编造，并保留人工复核要求”。
- 不要把哈希向量说成真实语义 Embedding。
- 不要说“线上准确率很高”；当前指标来自 24 条脱敏教学集。
- 不要把固定图节点包装成完全自主的 ReAct Agent。
- 不要说已经实现 MCP、Multi-Agent、长期记忆、SSE 或生产级队列。

## 3. Agent 核心问题

## Q1：什么是 AI Agent？它和普通大模型调用、RAG 有什么区别？

### 30 秒回答

> 大模型调用主要完成一次输入到输出；RAG 在生成前增加外部知识检索；Agent 则围绕目标维护状态，根据观察结果选择下一步行动，并调用工具或工作流节点，直到完成、失败或转人工。工程上我更关注状态、分支、工具契约、终止条件、恢复和评测，而不是是否使用了“Agent”这个类名。

### 结合项目展开

律镜不是一次 Prompt 完成全部事情，而是：

```text
案件抽取
  ├─ 信息不足 → 追问并暂停 → 回答后重新抽取
  └─ 信息足够 → 混合检索 → 引用审核
                              ├─ 无有效引用且未超限 → 补充检索
                              └─ 有引用或达到上限 → 生成报告
```

它具有显式状态、条件分支、外部知识检索、数据库校验、人工参与、重试上限和持久化恢复，因此比单次 LLM 或固定的“检索后生成”更接近工程化 Agent。

### 可能追问：那你的项目为什么不是普通流水线？

> 前半段确实有确定性流水线特征，我不会回避这一点。但它已经有两个由运行状态决定的循环：关键信息缺失时暂停并在回答后回到抽取；引用不足时有界返回检索。再加上 checkpoint 和人工恢复，它不是只能从头到尾执行一次的线性链。

## Q2：为什么需要 LangGraph？是否属于过度设计？

### 30 秒回答

> 如果只有“调用模型—调用接口—返回结果”三步，我不会使用 LangGraph。这个项目需要条件分支、检索重试、人工暂停、服务重启恢复和节点级轨迹，图的边正好对应真实业务状态，所以 LangGraph 帮我统一了状态演化、interrupt 和 checkpoint。代价是状态 Schema、序列化、框架表和调试复杂度增加。

### 结合项目展开

- `analyze_case` 后根据 `missing_information/questions_for_user` 路由。
- `clarify_user` 使用 `interrupt` 暂停。
- 回答后使用同一 `checkpoint_thread_id` 和 `Command(resume)` 恢复。
- `review_citations` 后根据有效引用数量决定写报告或补充检索。
- `MAX_WORKFLOW_RETRIES=2` 和 `MAX_CLARIFICATION_ROUNDS=3` 保证流程可终止。
- SQLite `SqliteSaver` 适合本地演示，生产环境会换 PostgreSQL checkpointer。

### 缺点要主动说

1. 框架内部 `checkpoints/writes` 表不适合业务直接查询；
2. interrupt 节点恢复时可能从节点开头重放，副作用必须幂等；
3. checkpoint 可能膨胀，需要状态裁剪、TTL 和敏感字段策略；
4. SQLite 不适合多进程高并发。

## Q3：Planning 是框架完成的，还是模型完成的？

### 30 秒回答

> 两者都可以参与，但职责不同。模型擅长根据自然语言生成或调整计划；框架负责可靠地执行计划，包括状态、依赖、超时、重试和终止条件。高风险业务不应把所有控制权交给模型。我的项目采用代码定义的宏观图，模型只负责节点内部的案件理解、语义审核和报告写作。

### 结合项目展开

律镜的“宏观 Planning”由 LangGraph 的节点和条件边确定，这是为了保证法条审核不能被跳过、重试次数有上限、信息不足必须追问。LLM 的自由度被限制在结构化输出内。

如果未来要支持更开放的法律任务，可以增加：

1. Planner 输出受限的步骤枚举；
2. 服务端校验步骤是否合法；
3. Executor 只执行允许的工具；
4. 每步观察结果反馈给 Planner；
5. 达到成本、轮次或风险阈值后转人工。

## Q4：常见 Agent 模式有哪些？你的项目属于哪一种？

### 回答

- Tool Calling：模型选择工具和参数，执行结果再返回模型。
- ReAct：Reasoning 与 Action/Observation 交替进行。
- Plan-and-Execute：先生成整体计划，再逐步执行。
- Reflection：生成后由模型或验证器复查、修正。
- Workflow Agent：路径主要由代码和状态机控制。
- Human-in-the-loop：关键节点暂停，由人确认、补充或审批。

> 律镜主要是 Workflow Agent + Human-in-the-loop + 受控 Reflection。引用审核节点相当于验证器，但当前不是开放式 ReAct，也不是模型自由选择任意工具。这样做是因为法律引用场景更重视可预测性和可审计性。

## Q5：详细讲一下 ReAct。为什么你的项目没有直接使用 ReAct？

### 30 秒回答

> ReAct 把推理与行动交错执行：模型根据目标产生行动，环境或工具返回观察结果，模型再更新下一步行动，直到给出答案。它适合工具集合较多、步骤难以预先确定的开放任务。律镜当前业务路径稳定，而且“引用审核”不能被模型绕过，因此使用显式图更可靠。以后可以在某个受限子图内引入 ReAct，而不是让它控制整个法律流程。

### 不要这样答

- 不要声称系统保存或展示模型的私有思维链。
- 可以展示工具名、参数摘要、结果、节点和耗时，但不应把隐藏推理当作产品日志。

ReAct 原论文强调的是推理轨迹与环境行动交替，而不是“只要循环调用模型就是 ReAct”。

## Q6：单 Agent 和 Multi-Agent 怎么选择？

### 30 秒回答

> 先看任务是否真的存在可独立并行的角色、不同权限、不同上下文或不同模型需求。如果只是固定的抽取、检索、审核步骤，用单图多节点更简单；强行拆成多个 Agent 会增加通信、上下文复制、冲突解决、成本和调试复杂度。只有角色边界清晰且收益可测时才使用 Multi-Agent。

### 结合项目展开

律镜当前是一个 LangGraph 工作流，不是多个自治 Agent。案件抽取、检索和审核是节点/服务，因为：

- 共享同一个案件状态；
- 大部分步骤顺序明确；
- 数据库权限相同；
- 没有必要为每步复制上下文和建立通信协议。

未来可以将“法规版本核验”做成独立 Agent，因为它可能使用不同数据源、权限和更新周期；但要定义消息 Schema、超时、重试、幂等键、冲突裁决和 trace 关联。

## 4. Tool、MCP、Skill 与 Memory

## Q7：Function Calling / Tool Calling 的完整流程是什么？

### 30 秒回答

> 应用先把工具名称、描述和 JSON Schema 发给模型；模型返回结构化工具调用意图和参数；应用校验工具是否存在、参数是否合法、当前用户是否有权限，再真正执行工具；工具结果作为 observation 回传模型，模型决定继续调用还是输出最终答案。模型只提出调用请求，真正执行和授权必须由服务端控制。

### 如何结合项目回答

> 当前律镜没有通用的“模型自主选工具”循环，而是 LangGraph 节点直接调用 Python 服务，例如混合检索、引用审核和报告生成。这减少了编造工具名和越权调用的风险。如果改成 Tool Calling，我会给 `search_laws`、`get_article` 等工具定义严格 Schema，只允许只读查询；知识库写入必须增加确认节点、RBAC 和幂等键。

### 如何防止工具幻觉

1. 工具白名单和稳定、清晰的 Schema；
2. Pydantic 参数校验和枚举；
3. 鉴权不能交给模型判断；
4. 写操作预览和人工确认；
5. 超时、重试上限、熔断和幂等；
6. 工具结果必须带来源，不能由模型伪造；
7. 记录工具调用成功率、参数错误率和耗时。

## Q8：MCP、Tool、Skill、Agent 分别是什么？

### 回答

| 概念 | 解决的问题 |
|---|---|
| Tool / Function | 一个具体能力如何被调用，例如查询法条 |
| MCP | Host、Client、Server 之间如何用标准协议暴露工具、资源和 Prompt |
| Skill | 如何把一类任务的说明、流程、工具使用方法和验收规则封装成可复用能力 |
| Agent | 谁根据目标和状态决定何时使用哪个能力，并负责执行闭环 |

> MCP 不是 Agent，也不会自动产生规划；它主要解决集成协议问题。Skill 也不能取代底层 Tool，因为 Skill 最终仍可能需要稳定的程序接口完成真实动作。

### 结合项目展开

当前项目通过内部 Python 函数调用知识库，没有接入 MCP。未来可以把“法律条文查询”暴露为只读 MCP Server，让其他 Agent 复用；但法律条文写入不应直接开放，必须加身份、权限、确认和审计。

## Q9：短期记忆、长期记忆、RAG 和 checkpoint 有什么区别？

### 回答

| 概念 | 内容 | 生命周期 |
|---|---|---|
| 短期/工作记忆 | 当前任务最近对话、工具结果、未完成计划 | 当前 thread |
| 长期记忆 | 用户偏好、历史经验、跨会话事实 | 跨 thread，需要写入门控 |
| RAG 知识库 | 法规、制度、文档等外部知识 | 随知识源更新 |
| LangGraph checkpoint | 某个 thread 的可恢复图状态 | 工作流执行与恢复 |

### 结合项目回答

> 律镜已经实现任务级 state 和 checkpoint，但没有用户级长期记忆。法规库属于 RAG，不是“用户记忆”。`sessionStorage` 只保存当前 run ID，也不等于 Agent Memory。后续如果做长期记忆，我会先增加用户身份和授权，再区分可保存事实、敏感信息、TTL、纠错和删除机制，不能把所有对话无条件向量化。

## Q10：LangGraph checkpoint、interrupt 和 resume 是怎样配合的？

### 30 秒回答

> 图编译时配置 checkpointer，每次图状态推进会按 thread 保存快照。节点调用 interrupt 后，当前状态和下一步位置被持久化，API 将业务状态设置为 waiting_for_user。用户回答后，系统用相同 thread_id 调用 Command(resume)，从中断点继续。checkpoint 负责图恢复，业务追问表负责前端查询、幂等和审计。

### 项目里的并发与重复提交

- `checkpoint_thread_id`：图存档标识，与 `run_id` 分开。
- `agent_clarifications`：保存问题、答案、轮次和幂等键。
- `Idempotency-Key`：同一网络请求重试不重复恢复。
- `state_version`：两个页面同时提交时只有一个条件更新成功，另一个返回 409。
- 最多三轮：避免模型持续提出相似问题导致无限等待。

### 面试官可能继续追问

**为什么业务表和 checkpoint 都要有？**

> checkpoint 适合框架恢复，不适合作为前端业务 API；业务表适合权限、状态查询、幂等和审计。二者职责不同。

**interrupt 节点能否先发消息、扣款，再 interrupt？**

> 不应该直接这么做，因为恢复可能重放节点。外部副作用应放在安全边界之后，或者使用业务幂等键。

## 5. RAG、Embedding 与检索

## Q11：完整讲一下 RAG 流程。你的项目有什么不同？

### 标准流程

```text
数据接入 → 清洗/解析 → 切分 → Embedding → 建索引
用户查询 → Query 处理 → 召回 → 融合/重排 → 构造上下文
LLM 生成 → 引用/事实校验 → 评测和 bad case 回流
```

### 结合项目回答

> 律镜当前的知识单元天然是一条法律条文，因此没有把一条条文再按固定 token 切碎。导入时保存法律名称、条号、来源和正文；向量索引按 provider、model 和正文 hash 管理。查询由案件问题、争议焦点和诉求组成，使用关键词与向量分数混合召回 Top-5。与普通 RAG 最大的差异是召回后还有引用审核：article ID、法律名称、条号、正文必须与数据库一致，Agent 模式还可以做语义支撑审核，最终报告只接收通过的引用。

### RAG “分类”怎么回答

这个问题可能有多种含义，建议先向面试官确认维度，再回答：

- 按召回方式：稀疏检索、稠密检索、混合检索；
- 按执行方式：一次检索的 2-step RAG、根据结果迭代的 Agentic RAG；
- 按数据结构：普通文本、层级索引、知识图谱 RAG；
- 按数据形态：文本、表格、代码、多模态 RAG。

律镜当前属于“条文级混合检索 + 有界反馈重试”，具有轻量 Agentic RAG 特征。

## Q12：Embedding 为什么能做相似度检索？模型怎么选？

### 30 秒回答

> Embedding 把文本映射到高维向量，使语义相关文本在向量空间中更接近。查询和文档使用同一模型编码后，可以用余弦相似度排序。模型选择不能只看榜单，要用自己的中文法律标注集比较召回率、MRR、维度、延迟、价格、批处理限制和部署方式。

### 结合项目回答

- 在线 provider 和离线 hash provider 分离；
- 向量记录 provider、model、dimensions 和 content hash；
- 法规正文变化或模型变化时需要重新建索引；
- 在线调用连续失败两次才回退 hash，并在轨迹中显示原因；
- 当前在线组没有纳入固定评测，因此不能宣称某在线模型效果最好。

### 为什么对正文 Embedding，而不是只对标题？

> 法律标题区分领域，但具体责任条件往往在正文里。律镜对正文生成向量，关键词侧同时使用法律名称、条号和正文。更成熟的方案可以分别编码标题、条号、正文和摘要，再通过字段权重或多路召回融合。

## Q13：为什么做混合检索？当前效果真的更好吗？

### 30 秒回答

> 关键词检索擅长精确法律名称、条号和关键措辞，向量检索擅长同义表达。项目按 `0.35 × keyword + 0.65 × semantic` 融合，但权重只是初始值，必须用标注集验证。当前 24 条离线教学集上，关键词 Recall@5 是 0.7639，hash 混合只有 0.6806，所以我不会说当前离线混合一定更好；结果说明哈希向量语义质量不足，在线模型与权重仍需单独评测。

### 为什么这反而是好的面试回答

它证明你没有只挑好看的数字。可以进一步提出：

1. 用真实中文 Embedding 运行 `online_mixed` 对照；
2. 网格搜索关键词/语义权重；
3. 按案件类型路由检索；
4. 增加 BM25 和 Cross-Encoder Rerank；
5. 扩充难例、干扰条文和同条号不同法律的数据；
6. 分析每个 bad case，而不只看总平均值。

## Q14：Top-K、切片和 Rerank 怎么设计？

### 回答

> K 越大通常提高召回机会，但也增加审核、上下文长度、延迟和噪声。律镜当前 Top-K=5，是教学规模下的工程起点，不是理论最优值。应该画出 K 与 Recall、MRR、Precision、延迟和 token 成本的曲线后再选。

当前法规以“单条法条”为最小知识单元，避免把适用条件截断。如果遇到司法解释长段落，可以采用：

1. 先按章/条/款结构切分；
2. 超长条文再递归切分并保留父级元数据；
3. 召回子块后回填完整条文；
4. 使用 Reranker 对初召回候选重新排序；
5. 保留 law name、article number、version 和 source 作为过滤字段。

项目目前没有 Cross-Encoder Rerank，面试时不能说已经实现。

## Q15：怎样减少 RAG 和法律回答的幻觉？

### 30 秒回答

> 我把“条文是否真实”和“条文是否支持问题”分成两层。模型只能看到检索候选，服务端再按 article ID 回查数据库，核对法律名称、条号和正文；Agent 模式可以继续判断语义支撑关系。报告只接收审核通过的引用，并明确标注证据缺口和非法律意见声明。

### 仍然不能保证什么

- 数据库中的法规是否仍然现行有效；
- 模型对事实与条文适用关系的法律判断绝对正确；
- 用户提交证据是否真实、完整；
- 召回是否覆盖所有相关条文。

因此生产化还需要权威法规版本同步、人工审批、引用有效期和审计记录。

## 6. 可靠性、评测与工程化

## Q16：Agent 为什么容易死循环？如何兜底？

### 原因

- 模型持续选择同一个失败工具；
- observation 没有反馈失败原因；
- 目标和完成条件模糊；
- 状态没有记录已经尝试过的动作；
- 工具错误被当作可无限重试的错误；
- 多 Agent 相互打回，没有仲裁和预算。

### 结合项目回答

> 律镜用显式终止条件控制循环：检索最多补充两次，追问最多三轮、每轮最多五问；LLM 结构化输出只修复一次；在线 Embedding 连续两次失败才回退；认证错误不做无意义重试。每次执行将实际 provider、模型、回退原因、节点耗时和错误码写入轨迹。

### 还可以增加

- 单任务总超时和 token/cost budget；
- 相同行动签名去重；
- circuit breaker 半开恢复；
- 队列级重试和死信队列；
- 低置信度或高风险操作转人工。

## Q17：用户意图模糊或关键信息不足怎么办？

### 30 秒回答

> 不应让模型猜测，也不应一次问十几个宽泛问题。我让案件抽取节点输出缺失字段和具体问题，图进入 interrupt；前端按轮次展示问题，用户可以回答“暂不清楚”。回答会带问题 ID 合并回原材料并重新抽取，最多三轮，达到上限后继续生成明确标注证据缺口的报告。

### 该设计的工程点

- 问题与业务字段关联；
- 每轮问题数量上限；
- 用户回答与原问题 ID 精确匹配；
- 页面刷新和服务重启后仍能恢复；
- “不知道”是合法答案；
- 状态版本与幂等键处理并发和重试。

这是本项目与淘天面经中“需求不明确时如何澄清”最直接的对应亮点。

## Q18：如何评测 Agent，而不是只看最终回答好不好？

### 30 秒回答

> 我把评测拆成节点级和系统级。抽取看案件类型准确率、关键事实和争议焦点覆盖；检索看 Recall@K、MRR、Hit@K、Precision@K 和延迟；引用审核看真实引用通过率和错误接受率；系统看成功率、P95、模型调用、回退率、重试率和人工介入率。还要保存 bad case，定位是数据、检索、模型还是工作流问题。

### 项目当前数据

- 24 条脱敏教学评测样例；
- 案件类型准确率：100%，仅代表当前小型教学集；
- 工作流成功率：100%，仅代表离线评测环境；
- keyword Recall@5：0.7639；
- hash semantic Recall@5：0.6458；
- hash mixed Recall@5：0.6806；
- online mixed：尚未执行固定评测；
- 自动测试：84 项。

### 下一步最重要的改进

增加食品安全、消费者权益和侵权等领域标注，区分简单、长尾、信息缺失和对抗样例；在线记录节点成功率、P95、provider 回退率和用户补充后完成率。

## Q19：Prompt Engineering 和 Context Engineering 有什么区别？

### 回答

> Prompt Engineering 主要设计指令、角色、输出格式和示例；Context Engineering 关注模型在这一次调用中究竟看到哪些信息，包括系统规则、用户问题、历史、检索候选、工具结果、Schema 和 token 预算。复杂 Agent 的效果往往更依赖上下文选择与隔离，而不只是措辞。

### 结合项目回答

- Prompt：要求只返回 JSON、不得创造 article ID、数组字段必须符合 Schema；
- Context：只把候选法条发送给审核模型，报告只接收已审核引用；
- 状态：追问答案合并回案件材料，而不是无限追加所有内部日志；
- 修复：Schema 校验失败时，把具体错误与 JSON Schema 作为第二次修复上下文；
- 安全：上传材料是数据，不应被当成高优先级系统指令。

## Q20：不用 LangChain/LangGraph，从零设计一个最小 Agent 怎么做？

### 回答

最小闭环需要：

```text
输入目标
  ↓
读取当前状态
  ↓
模型输出结构化 action
  ↓
校验 action、参数和权限
  ↓
执行工具并产生 observation
  ↓
更新状态和日志
  ↓
满足完成条件？否则继续
```

还必须有：

- 工具注册表和 JSON Schema；
- 状态存储；
- 最大轮次、总超时和成本预算；
- 失败分类、有限重试和人工接管；
- 幂等、副作用边界和审计；
- 离线测试与 Fake Tool。

> LangGraph 不是 Agent 的必要条件，它只是帮助实现状态图、持久化和恢复。先理解最小闭环，才能说明为什么选框架。

## Q21：系统在真实业务中能用吗？还有哪些生产缺口？

### 建议回答

> 当前是可独立运行的求职工程项目，可以演示完整链路和故障处理，但我不会说它已经是生产法律系统。现在使用 SQLite 和进程内 BackgroundTasks，等待用户回答的 checkpoint 可跨重启恢复，但任务正在检索或写报告时进程退出，不会被其他 Worker 自动接管。

生产化优先级：

1. PostgreSQL/pgvector 和正式迁移工具；
2. Redis/RabbitMQ 等持久任务队列、重试和死信；
3. 对象存储、病毒扫描、OCR 与数据保留策略；
4. 用户、租户、RBAC、配额、审计和加密；
5. 权威法规版本同步、失效标记和人工审批；
6. 分布式 trace、指标、告警、成本和回退率；
7. 灰度发布、模型/Prompt/索引版本和回滚；
8. 更大规模人工标注集与线上抽检。

## Q22：如果 SSE 断开，怎样让用户继续看到之前的输出？

### 回答

> 不能把浏览器连接本身当作任务状态。服务端应先创建持久任务和 event sequence，再由 Worker 执行；每个事件带 run_id 和递增序号写入持久存储。SSE 只是订阅层，客户端重连时携带 Last-Event-ID，服务端补发缺失事件，再继续推送。任务完成状态和结果必须能通过普通查询接口获取。

结合项目要诚实说明：

> 律镜目前使用轮询，不是 SSE。好处是页面刷新后可用 run ID 恢复；缺点是实时性和请求效率一般。将来改 SSE 时会保留现有状态查询接口作为断线兜底。

## Q23：如何做多租户隔离和 Agent 安全？

### 回答

多租户至少需要：

- 所有业务表带 `tenant_id`，查询强制注入租户条件；
- checkpoint thread 使用不可猜测 ID 并绑定 tenant/user；
- 向量索引按租户命名空间或物理隔离；
- 文件对象存储路径、缓存 key、日志和配额都带租户；
- Tool 使用服务端 RBAC，不相信模型输出的权限判断；
- 写操作最小权限、人工确认、幂等和审计；
- 对 Prompt Injection 做指令/数据分离、工具白名单、输出校验和监控。

结合项目：

> 当前项目只适合单机演示，没有账号和多租户。已有的基础防护包括上传大小/类型校验、结构化输出验证、知识库原文回查、写入不由模型自动决定、日志不记录密钥和案件全文。生产化必须补 RBAC、租户字段、工具权限与安全评测。

## Q24：为什么用 RAG，而不是微调/SFT？

### 30 秒回答

> 法规知识会更新，而且回答需要显示具体来源。RAG 可以更新外部知识库而不重新训练模型，也能把引用暴露给审核。SFT 更适合改变输出风格、任务格式和稳定行为，不适合作为频繁更新事实的唯一载体。二者可以组合，但当前项目的问题首先是知识可追溯和工程可靠性，所以优先 RAG。

### 结合项目回答

项目没有训练模型，不要讲 PPO、DPO 或 GRPO 的实战经验。若被问到，应明确：

> 我的项目属于 AI 应用工程，不是模型训练项目。对于当前 241 条教学法规，先完善数据、检索、审核和评测的收益高于训练。未来只有在积累足够高质量任务轨迹，并证明 Prompt、RAG 和后处理达到瓶颈后，才考虑对结构化抽取或路由做任务型微调。

## Q25：Trace 为什么不能直接记录完整 Prompt？Token 与费用等于账单吗？

### 回答

Prompt 和案件材料可能包含身份、地址、合同金额与商业秘密。监控系统通常保留更久、访问面更广，如果为了调试直接记录全文，会把可观测性变成泄漏通道。本项目使用 allowlist，只保留 run/thread ID、节点、provider/model、Token、计数和错误码。

Token 也不必然等于账单。服务商返回 usage 时优先使用真实计数，没有 usage 时只能明确标记为近似；费用按环境变量中的每百万 Token 单价估算。缓存、批量折扣、免费额度和服务商计费规则可能造成差异，所以面板用于工程容量与相对成本分析，不用于财务对账。

## 8. 一页速记

### 必须记住的项目数字

- 版本：1.2.0；
- 教学数据：36 条内置法规 + 200 条可批量导入的跨领域样例；
- 评测集：24 条；
- 自动测试：84 项；
- Top-K：5；
- 检索权重：keyword 0.35，semantic 0.65；
- 检索补充重试：最多 2 次；
- 追问：最多 3 轮、每轮最多 5 问；
- 上传：TXT、DOCX、带文本层 PDF，最大 10 MB。

### 必须主动承认的缺口

- 在线 Embedding 固定评测尚未完成；
- hash mixed 在当前集上没有超过 keyword；
- 没有 Cross-Encoder Rerank；
- 没有 MCP、通用 Tool Calling 和 Multi-Agent；
- 没有用户级长期记忆；
- 没有 SSE；
- 没有持久任务队列；
- 没有多租户、RBAC、生产法律数据自动同步和来源过期提醒。

### 最值得强调的四个亮点

1. 引用不是模型随便生成，而是 article ID + law version ID 回查、日期过滤与原文一致性审核；
2. 信息不足时真实暂停，回答后可跨后端重启恢复同一任务；
3. 报告生成后再次暂停审批，退回会保留旧版本，只有批准版本允许导出；
4. 模型、Embedding 和结构化输出失败被分层记录、有限重试并透明降级；
5. 一个 Trace ID 可定位节点 P95、实际模型、Token、估算费用和降级原因，且遥测不保存案件全文与密钥。
