# 求职材料与面试准备

## 简历项目描述

> 独立设计并实现可追溯法律 RAG Agent：使用 FastAPI、LangGraph、SQLAlchemy 与 React/TypeScript 构建材料上传、案件抽取、时态法规过滤、混合检索、引用审核、人工审批与 Markdown/PDF 发布闭环；接入阿里云百炼 `text-embedding-v4`，通过 OpenAI 兼容接口完成法规批量向量化和关键词-语义加权检索。以 `article_id + law_version_id` 约束模型引用，用追加式版本、幂等键和乐观锁处理审计、重试与并发；接入 OpenTelemetry，用 Trace ID 展示节点 P95、模型、Token、人民币费用与降级。构建 24 条脱敏评测集、36 条内置教学法规及 200 条跨领域法规 TXT 样例；当前样例上案件类型准确率 100%、关键事实关键词覆盖率 93.75%、离线工作流成功率 100%，关键词检索 Recall@5/MRR 为 0.7639/0.6736；84 项自动测试覆盖模型/向量回退、重启恢复、审批并发、法规日期边界、监控聚合和遥测隐私。

指标仅适用于当前教学数据集。阿里百炼 `text-embedding-v4` 已完成真实配置回归和引用审核链路验证，但尚未形成固定的在线向量对照评测结果，因此不应虚构在线 Recall/MRR 指标。

## 30 秒项目介绍

这个项目解决大模型法律回答中“法条可能编造、法规时点可能错、信息不足仍强行回答、模型草稿未经审核直接发布”的问题。我把流程拆成要素提取、用户追问、按案件日期筛选法规、阿里百炼 Embedding 驱动的混合检索、引用审核、报告生成和人工审批。回答与审批都能从 SQLite checkpoint 恢复；引用保留精确法规版本，只有批准报告可下载。每次运行还有脱敏 Trace，可查看最慢节点、模型、Token、人民币费用和降级原因。项目有 24 条脱敏评测集、36 条内置法规、200 条跨领域样例、84 项测试和 GitHub Actions CI。

## 重点项目挑战：多层智能回退与可观测性

> **这是本项目最值得在面试中重点展开的技术挑战。**

### 挑战背景

一次真实 Agent 运行同时出现三个现象：

- LLM 已成功调用，但案件类型返回“未识别”；
- 在线 Embedding 在首次为大量法规补建向量后发生瞬时超时，系统静默显示 `provider=hash`；
- 报告模型把应为数组的字段返回成字符串，Pydantic 校验失败后使用了离线模板。

这三个问题分属“语义判断、外部服务可靠性、结构化输出契约”三层。如果统一当成“模型失败”，既无法准确修复，也无法向用户解释实际使用了什么能力。

### 我的解决方案

1. 利用数据库中的节点轨迹、耗时、provider、模型名和错误码复盘单次运行，确认 `.env` 配置有效，区分配置错误与瞬时网络错误。
2. LLM 返回“未识别”时保留其事实、缺失信息和追问，只用确定性分类器补全案件类型，并标记 `source=llm_enriched`。
3. 在线 Embedding 第一次失败时在 provider 层重试一次，连续两次失败才使用 hash；回退原因写入 Agent 轨迹。
4. 提示词明确数组契约，二次修复携带校验错误和 JSON Schema；对“字符串代替字符串数组”的常见输出做受控归一化。
5. 用 Fake Provider 做完全离线自动测试，再用真实配置对“食物中毒商家需要负责吗”进行不写库回归。

### 量化结果

- 案件类型从“未识别”修复为“食品安全与消费者权益纠纷”；
- 最终检索使用 `openai-compatible / text-embedding-v4`，没有 hash 回退；
- 3 条法规引用通过真实性和语义审核；
- `deepseek-v4-flash` 成功生成结构化报告，没有模板回退；
- 自动测试从 44 项增加到 48 项，Ruff、mypy 和前端生产构建全部通过。

### 60 秒面试表达

> 项目中最有代表性的挑战，是一次运行同时发生了三种 AI 系统故障：LLM 返回合法但低质量的“未识别”，Embedding 瞬时超时后静默降级，报告模型又违反 JSON 数组契约。我没有简单关闭回退，而是先用持久化节点轨迹把问题分层。分类层采用 LLM 结果与确定性规则融合；向量层增加一次有界重试，连续失败才回退，并把原因写进轨迹；输出层把校验错误和 Schema 用于一次修复，对常见字符串数组错误做安全归一化。最后用 Fake Provider 做 48 项离线测试，再用真实模型回归，最终案件类型、在线检索、引用审核和报告生成全部通过。这个改动让我真正理解了 Agent 工程的重点不是调用模型，而是可观测、可验证和可解释地处理失败。

## 第五周面试亮点：可恢复的多轮追问

### 技术问题

原系统虽然能抽取 `missing_information` 和 `questions_for_user`，但工作流不会暂停，仍会带着信息缺口直接生成报告。普通聊天消息也不能回答“当前等待哪个问题、服务重启后从哪里继续、重复回答是否会执行两次”。

### 解决方案

1. 在 `analyze_case` 后增加条件分支，信息不足时进入 `clarify_user`；
2. 使用 LangGraph `interrupt` 暂停，使用 SQLite checkpointer 保存完整图状态；
3. 用 `checkpoint_thread_id` 把 checkpoint 与业务 `run_id` 关联；
4. 用 `agent_clarifications` 保存可查询的业务待办，不让前端直接依赖框架内部表；
5. 回答接口同时校验 `Idempotency-Key` 和 `expected_state_version`，处理网络重试和两个页面并发提交；
6. 通过 `Command(resume=...)` 合并回答并回到案件抽取，最多三轮后有界结束；
7. 前端使用 sessionStorage 找回当前任务，刷新页面后重新查询待办。

### 60 秒表达

> 第五周我把一次性法律工作流升级成了真正可暂停、可恢复的 HITL Agent。原来模型虽然返回缺失信息，但系统仍会直接写报告。我在要素提取后增加条件分支，调用 LangGraph interrupt，把 checkpoint 持久化到现有 SQLite；同时单独设计 agent_clarifications 业务表，让前端可以查询问题、轮次和状态版本。用户回答时用幂等键防止网络重试重复执行，用乐观锁防止两个页面同时提交，再用 Command resume 恢复同一个 thread。测试覆盖应用上下文重启恢复、重复回答、过期版本和三轮上限。恢复后仍能直接生成并下载当前最终报告，因此第五周本身就是完整功能，不依赖下一周审批。

## 第六周面试亮点：报告审批、版本管理与并发控制

### 技术问题

模型生成一份结构合法的法律报告，不代表事实理解、引用选择和风险提示已经正确。如果生成后立即开放下载，前端隐藏按钮也无法阻止用户直接调用 API；修改时覆盖原 Markdown 又会失去审计证据。

### 解决方案

1. `write_report` 后进入 `approve_report` interrupt，状态变为 `waiting_for_approval`；
2. `report_versions` 追加保存每版正文、事实和引用快照，`agent_approvals` 保存决定与意见；
3. 批准、要求修改和驳回都通过同一个审批接口，服务端校验状态机；
4. 要求修改进入 `revise_report`，创建 V2 后再次暂停审批，V1 保留为 `superseded`；
5. 导出接口只查询 `approved` 版本，不能靠绕过前端下载草稿；
6. `expected_state_version` 处理两个页面竞争，`Idempotency-Key` 处理同一请求网络重试；
7. 前端展示草稿标识、三种操作、版本历史和 unified diff。

### 60 秒表达

> 第六周我把模型输出从“生成即最终”改成了可审计的发布流程。报告写完后 LangGraph 再次 interrupt，业务表保存一个待审批版本。审核人可以批准、要求修改或驳回；修改不会覆盖原文，而是生成下一版本并再次审批。为了避免只做前端假按钮，导出接口只读取 approved 版本。并发方面我同时用了幂等键和状态版本：前者处理超时重试，后者用数据库条件更新保证两个页面只有一个审批成功。测试还关闭并重开应用上下文，证明等待审批的 checkpoint 能跨重启恢复。这样我能解释的不只是 HITL 交互，还有版本、并发、审计与发布边界。

## 第七周面试亮点：时态法规检索与版本证据链

### 技术问题

向量最相似的法条不一定在案件发生时有效。如果先召回 Top-K 再删除废止法，无效版本可能挤掉真正适用的历史或现行条文；只保存 `article_id` 也无法解释报告当时引用的是哪个法规版本。

### 解决方案

1. 用 `laws` 表示法规实体，用 `law_versions` 表示具体版本、生效/失效日期和替代关系；
2. 条文通过 `law_version_id` 绑定版本，案件和 Agent 保存可选 `as_of_date`；
3. 日期区间采用 `[effective_from, effective_to)`，解决生效日与失效日边界歧义；
4. SQL 在关键词与向量打分前过滤版本，避免无效候选占用 Top-K；
5. 检索结果、引用审核、日志和报告快照贯穿保存版本 ID；
6. 用《合同法》第九十四条与《民法典》第五百六十三条构造前后日期可重复演示；
7. 前端对历史条目标红为“已废止·历史时点适用”，同时展示适用区间。

### 60 秒表达

> 第七周我解决的是法律 RAG 中容易被忽略的时态问题：语义最相似不代表案件发生时有效。我把法规实体与版本拆表，用半开日期区间定义生效边界，并把过滤放在召回前，而不是 Top-K 之后。案件日期贯穿 Agent 状态，Citation 同时保存 article ID 和 law version ID，报告快照能证明当时引用的精确版本。同一个解除合同问题在 2020-12-31 返回历史《合同法》第九十四条，在 2021-01-01 切换为现行《民法典》第五百六十三条；留空则兼容按当前日期。测试专门覆盖边界日、废止版本排除和版本持久化。这个功能让我能把 RAG 从“相似文本搜索”讲到“业务约束下的时态检索和证据链”。

## 第八周面试亮点：Agent Trace、成本与隐私边界

### 技术问题

只有一条“模型失败”日志，无法判断慢在 LLM、Embedding、数据库检索还是工作流恢复；只显示最终 provider 也会掩盖在线模型曾经失败并回退。另一方面，直接把 Prompt 和案件材料写入监控系统会造成新的数据泄漏风险。

### 解决方案

1. 创建任务时复用 HTTP Trace ID，`agent.invoke` 与所有节点/模型 Span 保持同一 Trace；
2. 为案件抽取、Chat、Embedding、检索、引用审核、报告、重试和 HITL 恢复设置父子 Span；
3. 服务商提供 usage 时记录真实 Token，并用可配置每百万 Token 单价估算成本；
4. `agent_run_spans` 保存单次链路，`agent_runs` 保存概览所需聚合值；
5. 概览计算运行成功/降级率、总耗时平均/P95 和节点平均/P95；
6. Span 属性采用 allowlist，问题、材料、Prompt、密钥和身份信息一律丢弃；
7. 前端提供最近运行、最慢节点与 Span 瀑布，离线模式诚实显示 0 Token/费用。

### 60 秒表达

> 第八周我把“轨迹列表”升级成了能用于定位性能、回退和成本的可观测系统。创建请求的 Trace ID 会贯穿 LangGraph 根 Span、节点 Span、Chat 和 Embedding 调用；每个 Span 保存耗时、provider/model、Token、费用、重试和降级原因，监控页再聚合平均与 P95。成本不是写死的价格，而是按环境变量中的实际模型单价估算。更重要的是我没有把案件全文和 Prompt 当调试数据随便记录，而是用 allowlist 只保留低敏元数据，并有自动测试验证密钥和案件内容不会进入 Span。当前数据先落 SQLite，便于独立演示；生产化再接 OTLP Collector、Prometheus 和告警。

## 高频面试问题

### 为什么需要 Agent，而不是一次模型调用？

一次调用把抽取、检索、校验和写作混在一起，无法分别测试或重试。Agent 工作流的价值是显式状态、条件分支、工具调用和失败恢复，不是类名里出现 Agent。

### Agent 与普通流水线有什么区别？

案件抽取后可能进入多轮追问，引用不足时会回到检索，报告完成后会进入人工审批；审批要求修改又会回到报告修订。这些条件分支、两类 interrupt 和 checkpoint 恢复构成了明确状态机。若永远是固定顺序，普通流水线更简单，不应为框架而框架。

### 如何减少法条幻觉？

模型只能使用检索得到的 article ID 和 law version ID；服务端再核对 ID、版本、名称、条号和正文；报告只接收审核通过的引用。日期过滤减少引用失效版本，但仍需权威来源核对数据是否及时更新。

### RAG 如何评测？

固定脱敏数据集和相关 article ID，计算 Recall@5、MRR、Hit@K 与 Precision@5，同时记录延迟。抽取计算案件类型准确率和关键词覆盖率，系统层统计成功率、平均/P95 耗时和模型调用成本。

### 为什么选择 Top-K=5？

当前教学库已扩展到 200 余条，K=5 用于限制审核与报告上下文，同时保留足够候选。K 不是固定真理，应结合标注集绘制 K 与召回、精度、延迟和上下文成本曲线。

### 如何处理模型失败？

认证错误立即失败该次调用；限流和服务端错误有限重试；JSON 结构错误只修复一次；之后回退规则/模板并记录原因。CI 完全不访问真实模型。

### 如何保护上传文件？

前端校验用于体验，后端独立限制大小、扩展名、MIME、空文件和解析超时；文件名只作安全展示，不拼接路径；内容不进入 SQL 或系统命令；当前版本不持久保存上传原文件。

### 如何迁移到生产环境？

使用 PostgreSQL/pgvector、对象存储、持久任务队列、鉴权与租户隔离；加入法规版本同步、审计日志、指标告警和数据保留策略；通过影子流量与人工标注集验证迁移前后效果。
